## 指定檢查點

### (1) hidden / 鎖屏路徑 — ⚠️ 鎖屏 Play 受影響（W-514）

- **hidden 自動 reload**：本身就唔會（v1.20.8），`fetching` 唔改呢點；hidden tick 只係刷新 baseline。✅
- **hidden 凍結偵測**（v1.20.9 / C-011）：`isFrozenPlaying` 要 `playingFired` + rs ≥ 3，`stillFetching` 只喺 `playing` 未發、rs < 1 先生效，兩者互斥。✅
- **鎖屏 Play（S-614 `loading`）**：`loading → isStillLoading → isLoadProgressing → hasGrown`，`fetching` 只睇 `after`（狀態，唔係增長），所以 metadata 前只要 `NETWORK_LOADING` 而未收過 `stalled`，`loading` 就係 true → `isStuck()` false → 淨 `play()`（S-621 會記 `keep … loading`）。repro：hidden 開播、`startFetching()`、metadata 未到、冇 `stalled`，15 s 撳鎖屏 Play → `8052490` `load` 0 次；`8052490~1` 1 次。
- 係咪啱？S-614 嘅原意係「下載有進展先唔 reload」；`fetching` 唔係進展證據，只係「未見到失敗證據」。喺 iOS 鎖屏，JS 被凍結，就算 WebKit 有發 `stalled`，佢都係排喺隊入面，同 mediaSession `play` handler 邊個先行冇保證（同 W-511 / W-512 / CUI-0012 同一類）；如果 iOS 根本唔發，就要等到 30 s。S-551 嘅「鎖屏停喺 0:00 撳 Play 即 reload」正正係呢條路。

### (2) W-500 — ✅

`stillFetching` 限 `readyState < HAVE_METADATA`；metadata 一到就由 `buffered` / rs 話事，「metadata 到咗 → 4 s 照重試」有 test（F5 紅）。`HAVE_METADATA` 唔當進展嘅規則冇郁。

### (3) S-551 情境 1（轉網絡）喺 Chromium — ✅

Chromium hang 時 `progress` timer 約 3 s 發 `stalled` → `stalledSinceLoad = true` → 第一個 deadline（4 s）`fetching` false → 照舊 `retryNow()`（F2 / F6 紅）。如果轉網絡令 request 直接出錯，`error` → `onError` 停睇住，`online` → `recoverSource`，同之前一樣。

小注意（唔開 ID）：如果數據喺 t ≈ 2 s 先停，`stalled` 喺 ~5 s 先到，首個 deadline（4 s）仍然見 `fetching` → 推遲到 8 s。上限細、前景，屬用戶接受嘅風險範圍。

### (4) iOS `networkState` 會唔會令 `fetching` 黐住 true — 有可能，但有上限

- spec：冇數據入時 `networkState` 仍然係 `NETWORK_LOADING`，要等 3 s 冇進展先發 `stalled`（`networkState` 唔變）；資源完全載完 / preload 暫停先轉 `NETWORK_IDLE`（`suspend`）。所以「死咗但仲 LOADING」係 spec 正常狀態，靠 `stalled` 分辨。
- WebKit（AVFoundation）實作有 `progressEventTimer` 發 `stalled`，但冇實機 log 證實 iOS 喺 metadata 前、轉網絡時會唔會發 / 幾時發（ticket 已列「待實機確認」）。最壞情況 iOS 唔發 → `fetching` 一路 true。
- 上限：`isStillLoading` 要 `Date.now() - startedAt < STALL_MAX_WAIT_MS`，`startedAt` 係今輪 `start()`（唔係每次嘗試），所以：前景首次重試最遲 30 s；之後 cap 過咗，每 8 s 照常重試、扣次數；鎖屏 Play 30 s 後照 reload。唔會無限黐住。`stalledSinceLoad` 一經設定就成個載入都唔清，所以唔會「stalled 之後又變返 fetching」。

## 指定檢查：亮屏後 `onDeadline` 見 `fetching = true` 而 re-arm

- 路徑：hidden 期間 metadata 未到 → hidden tick 只刷新 baseline（`fetching` false，唔重要：`hasGrown` 只睇 `after.fetching`）→ 亮屏 `visibilitychange → retryIfOverdue → onDeadline` 前景分支 → 而家 visible、`NETWORK_LOADING`、未收 `stalled` → 當仲載緊 → `arm(nextRecheckMs())`，唔 reload。
- 呢個同用戶接受嘅風險一致：佢接受嘅就係「前景、metadata 前、未見 `stalled` 就當載緊，最多等 `STALL_MAX_WAIT_MS`」。亮屏之後頁面已經係前景，唔再有「JS 凍結、Play handler 同 `stalled` 搶先」嘅問題：如果 iOS 喺鎖屏期間已經發咗 `stalled`，解凍後佢會喺下一個 recheck（≤ 4 s）之前派發，下一次 deadline 就照 retry；如果 iOS 根本唔發，就最多等到開播後 30 s。兩種都喺「前景首次重試推遲，最多 30 s」入面，亦唔會 abort 一個真係慢載緊嘅 header（正正係 CUI-0011 想保護嘅）。
