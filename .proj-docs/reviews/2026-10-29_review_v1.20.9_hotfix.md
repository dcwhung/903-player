### 🟡 Warning

#### W-506 — `FROZEN_PLAYING_MS` 2 s 對 tick 相位嘅誤殺餘量只得 ~0.8 s

- 位置：`src/config/constants.ts` `FROZEN_PLAYING_MS`；`src/player/AudioController.ts` `isFrozenPlaying()`；`src/player/stallWatchdog.ts` `onDeadline()`
- 描述：hidden 時每個 tick（4 s 首個 deadline，之後每 4 s）只要「距 `playing` ≥ 2 s 而 ct 行咗 < 0.3 s」就 reload。若 `playing` 啱啱喺 tick 前 ~2 s 發（鎖屏快載 ~2 s），而 iOS 出聲比 `playing` 遲 > ~1.7 s，健康嘅接住播會被 reload（probe 證實）。log 實測出聲延遲 ~0.9 s。
- 影響：命中時重現 v1.20.7（hidden reload → 背景可能再唔載完 → 鎖屏接住播壞）。機率低（要快載 + 慢出聲 + 相位對齊），但後果係用戶最在意嘅功能。
- 方案 A：將 hidden 用嘅門檻拉到 ~4 s（例如 `FROZEN_PLAYING_MS = 4000`，或者另開 `FROZEN_PLAYING_HIDDEN_MS`）。優：一行改動；log 0.9 s 有 ~4× 餘量；用戶 log 嘅凍結 case 仍然喺下一個 tick（~8 s）或者下一次 pause → Play 救返。劣：凍結 case 遲 ~4 s 先救；test 邊界數字要跟住改。
- 方案 B：兩次取樣：第一次見「似凍結」只記低 `{ at, currentTime }`，下一個 tick / `onStopped` / `resume` 再見 ct 完全冇變（`===`）而相隔 ≥ `FROZEN_PLAYING_MS` 先算凍結。優：以「位置真係冇郁」做證據，同出聲延遲長短無關。劣：多一個 state，`onStopped` 同 `resume` 要決定用唔用單次判斷。
- 推薦：A 做下一個 patch（簡單、可量化），同時喺播放 log 嘅 `retry` 行附加 `since playing=…ms`，收真機數據再考慮 B。

#### W-507 — 冇「timeupdate throttled 嘅健康鎖屏接住播」regression test

- 位置：`src/player/AudioController.test.ts` `locked auto-advance (v1.20.8)` / `hidden frozen playing (v1.20.9)`
- 描述：見 (5)。`isFrozenPlaying` 必須讀實時 `audio.currentTime` 先唔誤判，但冇 test 會因為改壞呢點而紅。
- 影響：將來 refactor 可以靜靜打爛 v1.20.8 嘅保證。
- 方案 A：喺 v1.20.8 describe 加一個 case：`lockedAdvance()` → 4.3 s `emitPlaying(HAVE_ENOUGH_DATA)` → 只設 `audio.currentTime`（唔發 timeupdate）逐步行到 8 s 以上 → 5.5 s 先 `emitTime` → 期望 `load` 冇叫、`isStalled` false。優：直接鎖住用戶問嘅保證。劣：要手動行時鐘。
- 方案 B：喺 `FakeAudio` 加 `advanceSilently(seconds)` helper，再寫 A。優：日後易用。劣：改 test helper。
- 推薦：B（helper 細，之後 W-506 嘅邊界 test 都用得着）。

### 🟢 Suggestion

#### S-616 — 「數據喺本機，reload 唔會 abort 下載」講法唔準

- 位置：`src/config/constants.ts` `FROZEN_PLAYING_MS` doc、`stallWatchdog.ts` `isFrozenPlaying` hook doc、`AudioController.isFrozenPlaying` doc
- 描述：`audio.load()` 會清走 buffer、由網絡重新攞（最多靠 HTTP cache）。真正理由係「冇嘢載緊可以 abort，而唔 reload 就永遠救唔返」，唔係「reload 冇代價」。照現時寫法，之後有人可能以為 hidden reload 係安全而再放寬。
- 方案 A：改做「唔係載緊（冇下載會被 abort）；唔 reload 就永遠凍結，所以值得冒 reload 後背景載唔完嘅險」。方案 B：連 W-506 一齊改，順手寫埋 log 出聲延遲 0.9 s 做門檻依據。推薦：B。

#### S-617 — `onSilent`（waiting / emptied）重設 `audibleFrom` 但冇重設 `playingAt`

- 位置：`src/player/AudioController.ts` `onSilent()` / `onPlaying()`
- 描述：hidden 未 cancel 期間如果 `waiting` 發咗而 rs 仍 ≥ 3、之後冇再發 `playing`，凍結時鐘會由舊 `playing` 計，`advanced` 卻由 waiting 嗰刻計，會早過 2 s 判凍結。正常 `waiting` 會令 rs 跌到 ≤ 2、恢復時再發 `playing`，所以實際機會好低。
- 方案 A：`onSilent` 一併設 `playingAt = Date.now()`。方案 B：`onSilent` 清 `playingFired`，等下一個 `playing`。推薦：A（唔影響 S-583 嘅 playingFired 語義）。

```ts
// src/config/constants.ts
/**
 * 發咗 playing、readyState ≥ HAVE_FUTURE_DATA 而位置咁耐都冇行：當 pipeline 死咗（S-551 情境 2）。
 * 唔係載緊（冇下載會被 abort），唔 reload 就永遠凍結，所以鎖屏都 reload（v1.20.9）。

export const FROZEN_PLAYING_MS = 4000;

// src/player/AudioController.ts
private onSilent = (): void => {
    this.audibleFrom = this.audio.currentTime;
    // 凍結時鐘同位置起點一齊由而家計，唔好用舊 playing 嘅時間（S-617）
    this.playingAt = Date.now();
    this.update({ isAudible: false });
};
```

#### W-508 — `FROZEN_PLAYING_MS` = `STALL_FIRST_RETRY_MS`：真實時序下首個 deadline 永遠唔會判凍結

- 位置：`src/config/constants.ts` `FROZEN_PLAYING_MS`；test「reloads at the first deadline while locked when playing froze with the data present」（AudioController + usePlayer）
- 描述：`playing` 一定喺 `resume()` 之後先到（log 22 ms），所以 4 s deadline 時距 `playing` 一定 < 4 s。救援要等 8 s tick（iOS 未必畀 JS 行）或者用戶再 pause / Play。test 喺同一毫秒發 `playing`，令佢睇落係 4 s reload。
- 影響：log 情境照救得返（用戶 6.9 s pause），但如果用戶撳完 Play 唔再郁、iOS 又唔畀 8 s timer 行，就要等亮屏。常數註解同 test 名都講緊 4 s，唔準。
- 方案 A：`FROZEN_PLAYING_MS = 3500`。log 情境 4 s deadline 時 3978 ≥ 3500 → 首個 deadline 就 reload；最差相位誤殺要出聲比 `playing` 遲 > 3.2 s（log 0.9 s，~3.5× 餘量）；兩個 `setSystemTime(+FROZEN_PLAYING_MS)` test 會返去 deadline 之前，自動修好 W-509。test 要喺 `resume()` 後先行 22 ms 再發 `playing`。優：一個常數、同時解 W-508 / W-509。劣：餘量由 4× 跌到 3.5×。
- 方案 B：保持 4000，改 test 用真實 22 ms 時序、名改做「at the next hidden tick」、註解寫明首個 deadline 唔會 reload。優：誤殺餘量最大。劣：救援慢 4 s，靠 iOS 畀第二個 timer 行；W-509 要另外補 test。
- 推薦：A。
