## 問題清單

### 🟡 W-505 — metadata 之後嘅 `progress` 都算進展：W-500 情境首次重試由 4 s 變 8 s

- 位置：`src/player/loadProgress.ts` `hasGrown()`，`const gotBytes = after.progressEvents > before.progressEvents;`
- 描述：`gotBytes` 冇睇 `readyState`。W-500 刻意令「只有 metadata（rs 0→1）」唔算進展，因為情境 1（轉網絡 / 鎖屏自動接住播）通常係 header 載到、之後乜都冇嚟。但 header bytes 入嚟嗰陣 element 會發 `progress`（開發者量度：Chromium 喺 `loadedmetadata` 之後先開始發；iOS 未知但只會更早），於是同一個情境依家會經 `gotBytes` 當進展。
- Reviewer probe（臨時 test，已刪）：開播 → 500 ms `emitMetadata()` + 一個 `emitProgress()` → 之後靜晒：**4 s load 0 次、8 s 先 load 1 次**。改動前（W-500）係 4 s。現有 W-500 測試 `retries a stalled auto-advance at the first timeout when only metadata arrived` 冇發 `progress`，所以睇唔到。
- 影響：S-551 情境 1 首次重試落返 8 s，正正係 W-500 / S-583 想避開嘅 iOS 鎖屏 JS 凍結時段；換返嚟嘅好處（Chromium slow-header）實際上冇（Chromium metadata 前唔發 `progress`）。
- 方案 A（推薦）：只喺 metadata 未到時計 `progress`，即係 CUI-0011 本身嘅缺口；metadata 到咗之後 `buffered` / `readyState` 已經公開，`progress` 冇新資訊。
    ```ts
    // CUI-0011：metadata 未到（rs 0）先睇 progress；到咗之後 buffered / readyState 已公開，
    // 再計 progress 會令「只有 header」都當進展，情境 1 首次重試推到 8 s（W-500）
    const gotBytes =
        after.readyState < HAVE_METADATA && after.progressEvents > before.progressEvents;
    ```
    再補 controller 測試：`emitMetadata()` + `emitProgress()` 之後靜晒 → 4 s 重試；同 unit test `should not be progressing on progress events once metadata arrived`。Reviewer 喺 scratch 套用：`src/player` 212/212 綠 + 上面 probe 4 s 重試 ✔（已還原）。Trade-off：iOS 如果 metadata 之後 `buffered` 都唔郁（未知）就睇唔到嗰段；但嗰段 W-498 一直係咁，唔係今次範圍。
- 方案 B：controller 記 `lastProgressAt`，probe 只喺「最近 ~1 s 內有 `progress`」先算（spec 350 ms 一次，真 trickle 一定新鮮）。好處：連「metadata 前一小段 bytes 之後斷咗」（reviewer probe B：一個 pre-metadata `progress` → 8 s 重試）都 4 s 重試。Trade-off：多一個 `Date.now()` 狀態同常數；iOS 凍結 JS 時 event 排隊、解凍先一齊發，「新鮮」判斷會受影響，要實機先知。
- 推薦：A（一行、確定性、同 doc comment「metadata 未到時唯一嘅下載訊號」一致）。B 等 iPhone log 再考慮。

## Design note：`stalled` 規則（同意延遲）

開發者提嘅規則：metadata 前 + `NETWORK_LOADING` + `loadstart` 之後未見過 `stalled` → 當進展。

- 佢正正補到 Chromium repro（Chromium 有 bytes 就唔發 `stalled`，冇 bytes 約 3 s 發），理論上係 CUI-0011 嘅真修正。
- 但佢係「冇 event = 進展」嘅反向邏輯：`stalled` 唔發 / 遲發（iOS 對 `stalled` 嘅行為未有任何 log 證據；Chromium 3 s 門檻同 4 s deadline 只差 1 s，鎖屏時 timer 一遲就會錯過），情境 1 首次重試會一路推到 `STALL_MAX_WAIT_MS`（30 s）。後果比 W-505 大好多。
- `stalled` 已經喺 `MEDIA_EVENTS` 入面記 log，加上今次嘅第一個 `progress` 行，下一份 iPhone log 足夠決定。CUI-0011 係 🟢 Low（最後都播到），等證據合理。

結論：同意延遲；如果之後要做，建議同 W-505 方案 A 一樣限 `readyState < HAVE_METADATA`，並且要有「`stalled` 冇嚟」嘅上限（例如只喺首個 deadline 延一次），唔好直接靠 30 s cap。

## 修訂後代碼（`src/player/loadProgress.ts` 相關部分）

```ts
import { STALL_DATA_AHEAD_SECONDS } from '../config/constants';
import { HAVE_CURRENT_DATA, HAVE_FUTURE_DATA, HAVE_METADATA } from './mediaReadyState';

/**
 * 有新數據：buffer 尾增長；或者（未發 playing 時）readyState 升到有可播數據，
 * 或者 metadata 未到而有新 progress event（S-601）
 */
const hasGrown = (before: LoadProbe, after: LoadProbe): boolean => {
    const endBefore = before.bufferedEnd ?? Number.NEGATIVE_INFINITY;
    const endAfter = after.bufferedEnd ?? Number.NEGATIVE_INFINITY;
    if (after.playingFired) {
        return after.readyState < HAVE_FUTURE_DATA && endAfter > endBefore;
    }
    const gotData = after.readyState >= HAVE_CURRENT_DATA && after.readyState > before.readyState;
    // W-505：metadata 未到（rs 0）先睇 progress；到咗之後 buffered / readyState 已公開，
    // 再計 progress 會令「只有 header」都當進展，情境 1 首次重試推到 8 s（W-500）
    const gotBytes =
        after.readyState < HAVE_METADATA && after.progressEvents > before.progressEvents;
    return endAfter > endBefore || gotData || gotBytes;
};
```
