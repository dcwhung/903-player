## 指定檢查點

1. **watchdog / stall 狀態機 regression**：
    - `nextRecheckMs()` 只會喺 `isStillLoading()` true 時叫，而嗰度要求 `now - startedAt < STALL_MAX_WAIT_MS`，所以 `untilCap > 0`，唔會排 0 或負數 timer ✔。cap 嗰下 `withinCap` 係 `<`，所以剛好 30 000 ms 判 false → `retryNow()` ✔。
    - `startedAt` 只喺 `start()`（未 pending）設定；`retryNow` 之後 `watch(STALL_RETRY_MS)` 唔郁 `startedAt`，所以重試之後嘅 recheck 都以同一個 30 s 為上限，之後全部直接重試，仍然有界 ✔。
    - 重試之後嘅 baseline：`retryNow` 先 `hooks.retry()`（`reload()` → `audio.load()` 將 `readyState` 設 0）再 `watch()` → `arm()` 取 baseline，所以每一輪都由 `rs=0` 比較；W-500 之後 0→1 唔再推遲 ✔。
    - `stopWatchingStall()` 加入 `onError` / `play()` catch：兩處之前都已經 `playIntent = false`，`canRetry()` 會令下一個 deadline 自己 `cancel()`；今次只係提早 cancel 加清 `isStalled`，冇改變重試次數 ✔。
2. **S-581：重試入面 `play()` 被拒會唔會漏報卡住？** 唔會。Reviewer probe（臨時 test，已刪）：開播 → `playing` → `rejectPlay = true` → 4 s watchdog 重試（`load` 1 次、`play()` 被拒）→ snapshot `isPlaying:false, isStalled:false, intent:false`；之後 24 s 冇再 reload。
    - 鎖屏狀態由 `useMediaSession.ts:63` `isPlaying && !isStalled ? 'playing' : 'paused'` 決定；`isPlaying` 已經係 false，`isStalled` 係咪 true 對鎖屏冇分別，都係顯示 Play。即係「已經停咗」嘅事實仍然有反映，冇騙用戶話播緊。
    - 重試次數：修正前被拒之後 `playIntent` false，下一個 deadline `canRetry()` false 一樣會 `cancel()`，所以本身就唔會再自動重試；行為冇變。
    - 反而有改善：修正前 watchdog 仲 pending，用戶之後撳 Play 嘅 `start()` 係 no-op，會沿用舊 deadline 同剩低次數；而家已 cancel，用戶再撳係新一輪（probe：再撳後 3 999 ms 未 reload、4 000 ms reload 並標 `isStalled`，次數重新計）✔。
    - `isLatest()` 保護：`reload()` 嘅 `load()` / `switchTo` 換 src / `pause()` abort 舊 `play()` 時，新 `play()` 已經 `++playGeneration`，舊 rejection 唔會誤清新一輪；用戶暫停 abort 自己嘅 `play()` 時清 watchdog，同 `onPause` 本身做嘅一樣 ✔。
    - 兩次 `update()`（先 `isStalled:false` 再 `isPlaying:false`）喺同一個同步 block，React 18 會 batch，`useMediaSession` effect 唔會見到中間 `playing` 狀態 ✔。
3. **FakeAudio realism**：`src` setter / `load()` 設 `HAVE_NOTHING` 同 spec load algorithm 一致；`emitMetadata` 用 `Math.max(…, HAVE_METADATA)` 唔會降級；新 `emitLoadedData` 升到 `HAVE_CURRENT_DATA` 並發 `loadeddata` ✔。`emitPlaying()` 刻意唔郁 `readyState`，理由係 S-551 iOS「發咗 playing 但冇數據」；但按 spec，`playing` 正常喺 `readyState` 到 HAVE_FUTURE_DATA（3）先發，冇裝置 log 證明 iOS 嗰陣 `rs` 係 0/1（`playbackLog` 有記 `rs=`，但 docs 冇相關記錄）。見 S-583。
4. **chisee tile（`acd8ea5`）**：`git show --name-status` 只有 `M src/dramas/chisee/tile.webp`，冇掂其他 drama 檔 ✔。六個 `tile.webp` 全部 RIFF/WEBP `VP8 `（lossy）、**1216×608** ✔；新檔 52 788 B（舊 49 492 B），喺其他 tile 28.6–141 KB 範圍內 ✔。目視：黃底、角色同大 logo 喺左中，右上角另有一個細 logo（原圖帶嚟，用戶自己揀，冇問題，只係提一提 shelf 上面如果有疊字要留意）。

### 🟢 Suggestion

#### S-583 `FakeAudio.emitPlaying()` 唔模擬 `readyState`，「`playing` 已發 + 少量 buffer + 位置凍結」路徑冇測試，嗰度首次重試係 8 s

- 位置：`tests/fakeAudio.ts` `emitPlaying()`；相關邏輯 `src/player/loadProgress.ts` `isLoadProgressing`
- 描述：真瀏覽器 `playing` 通常喺 `readyState` ≥ 3 先發。Reviewer probe：開播 → `readyState = 4`、`buffered [0,5]` → `emitPlaying()`、位置唔行 → 4 s 冇重試（0→4 算進展、前面 5 s < 10 s）、**8 s 先重試**。即係 S-551 情境 2 如果 iOS 只載到少過 10 s 數據就凍結，首次重試仍然落喺 8 s，正正係 W-500 想避開嘅 iOS 凍結 JS 時段。
- 責任：W-498 / W-500 之前已經係咁（0→4 一直算進展），唔係今次 regression；W-500 只處理咗 `rs=1`。而家 `emitPlaying` 唔郁 `readyState` 令所有 controller 測試都睇唔到呢條路徑。
- 影響：鎖屏情境 2 + 少量 buffer 時可能由「鎖屏自己接返」退化成「亮屏先接返」；有冇呢個情況要睇實機 `rs=` / `buf=` log。
- 方案 A（推薦，先量度）：加一個 controller 測試鎖住而家 8 s 行為（標明係已知 trade-off），下一次實機測試時睇 `playing` 嗰行 log 嘅 `rs` / `buf`；如果真係出現先改邏輯。
    - Trade-off：零風險，但如果情況存在仍然慢 4 s。
- 方案 B：`playing` 已發而位置未行嘅話，`readyState` 增長唔當進展，只睇 `bufferedEnd` 增長（`StallWatchdog` 加 hook 例如 `hasStartedPlaying()`，或者 probe 帶 `playingSince`）。
    - Trade-off：情境 2 一定 4 s 重試；但前台慢網剛發 `playing` 而 timeupdate 遲咗少少都會被 reload 一次，同時令 W-498 嘅「慢網唔 abort」變弱。
- 方案 C：`emitPlaying()` 預設將 `readyState` 升到 HAVE_FUTURE_DATA，另加 `emitPlayingWithoutData()` 專俾 S-551 iOS 測試。更貼近 spec，但會郁好多現有測試嘅前提，要逐個睇。
