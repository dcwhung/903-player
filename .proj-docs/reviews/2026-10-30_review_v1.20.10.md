### (1) v1.20.7 regression（鎖屏 reload abort 載入）— ✅ 改善咗

S-614 之後鎖屏 Play 只喺 `isFrozenPlaying()`，或者「懷疑卡住 **而** `!stall.loading`」先 reload；`frozenBeforeStop` 亦由 `isStuck()` 計，所以 pause → Play 期間慢載唔會再被 abort。M4 證實 test 鎖住。注意 W-510：「loading」嘅判斷基準係 arm 嗰陣，鎖屏時通常係開播嗰刻。

### (2) v1.20.8 鎖屏自動接住播 — ✅ 冇 regression

`onDeadline` hidden 分支邏輯冇改，mark 前照舊每 ≤ 4 s 睇一次、唔 reload、唔扣次數；`deadline` 依然唔推後，`overdue` 照樣畀亮屏 / 鎖屏 Play 用。`stallEdgeCases.test.ts` 同 v1.20.8 describe 全綠。

### (3) v1.20.9 AirPods case（數據齊、playing 後凍結）— ⚠️ 鎖屏 Play 仍然救到；「到期自動 reload」有窗口失效（C-011）

- 鎖屏 Play：`resume()` 即時讀 `isFrozenPlaying()`（實時 `audio.currentTime`），同 timer 無關 → ✅ 照 reload。
- `onStopped` 記 `frozenBeforeStop` → ✅ 照舊。
- 到期自動 reload：mark 之後冇輪詢，淨係靠 `onPlaying → recheckWhenParked(FROZEN_PLAYING_MS)`。以下兩種情況會漏，見 C-011：
    1. `playing` 喺 mark 前 0 – 3.5 s 到（例如 hidden 開播後 10 s）：嗰陣 timer 仲排緊（mark tick），`recheckWhenParked` no-op；12 s mark tick 時未夠 3.5 s → park，之後再冇 timer。
    2. park 咗之後 `playing` → `waiting`（S-617 重設 `playingAt`）→ `playing`：第二個 `playing` 時第一個 recheck timer 仲排緊 → no-op；第一個 recheck 到期時由新 `playingAt` 計未夠 3.5 s → 再 park，冇 timer。

### (4) `recheckWhenParked` 會唔會令前景提早 retry — ✅ 唔會

- guard `pending && hiddenStallReported && timer === undefined`：`timer === undefined` 而 pending，只會喺 `waitWhileHidden` park 咗之後出現；park 要求 `onDeadline` 已經行過，即係 `now ≥ deadline`，而 hidden 期間 deadline 唔會推後 → 任何由 recheck 觸發嘅 `onDeadline` 都唔會早過原本 deadline。
- 亮屏：`onVisibilityChange → retryIfOverdue`，park 時 `overdue` 必然 true → `onDeadline` 前景分支：仲載緊就 `arm()`（timer 重設），否則 `retryNow()`（`startAttempt` 清 `hiddenStallReported`）→ recheck 之後一定 no-op。
- 就算 visibilitychange 冇發、recheck 喺前景到期，`onDeadline` 前景分支仍然先睇 `isStillLoading()`，同 W-498 一致，而且已經過咗 deadline，唔算「提早」。
- M5 顯示 `hiddenStallReported` 呢個條件其實多餘（equivalent mutant），見 S-618。

### (5) S-614 之後鎖屏顯示 Play、`isStalled` 仍然 true — 判斷：可以接受

- 顯示 Play 係事實（冇聲）；再撳 Play → `resume()` → `play()`：element 已經播緊，`audio.play()` resolve、`watchStall → stall.start()` 喺 pending 時 no-op，唔會補返重試次數，亦唔會 abort 下載 → 重複撳冇副作用。
- 真係出聲 → `checkAudible → stopWatchingStall` 清 `isStalled`，鎖屏轉 Pause。過咗 `STALL_MAX_WAIT_MS` 仲未出聲 → 下一次 Play `loading` false → reload。
- 如果反過來清走 `isStalled`，鎖屏會顯示 Pause，用戶撳 Pause 反而會停咗個慢載，更差。
- 唯一缺點係用戶撳完「冇反應」，log 又冇記低今次係刻意唔 reload（S-621）。

## 問題清單

### 🔴 Critical

#### C-011 — S-613 拆走 mark 後輪詢，令 v1.20.9 hidden 凍結自動 reload 有窗口失效

- 位置：`src/player/stallWatchdog.ts` `waitWhileHidden()` / `recheckWhenParked()`；`src/player/AudioController.ts` `onPlaying()` / `onSilent()`
- 描述：v1.20.8 review 寫 S-613 時，mark 後嘅 tick 確實冇獨有用途；但 v1.20.9 之後，hidden tick 係 `isFrozenPlaying()` 自動 reload 嘅唯一入口。今次用「`playing` 時排一次 recheck」取代輪詢，但 recheck 只喺「已 park 而冇 timer」時先排，亦只排一次，所以：
    1. `playing` 落喺 mark 前 `FROZEN_PLAYING_MS` 內 → mark tick 判未凍結 → park → 冇 timer。
    2. park 後 `playing → waiting → playing`（buffer 抖一下）→ 第二個 `playing` 排唔到新 recheck；第一個 recheck 以新 `playingAt` 計未夠 → park → 冇 timer。
- 證據：臨時 repro test（跑完已刪）喺 v1.20.10 兩個 case 都 `load` 0 次；將 `stallWatchdog.ts` + `AudioController.ts` 換返 `17baeb8`（v1.20.9）同一個 test 全綠（30 s 內有 reload）。repro 骨架：
    ```ts
    // hidden 開播、metadata 到；10 s 先 playing（rs=4），之後位置唔郁
    vi.advanceTimersByTime(10000);
    audio.emitPlaying(HAVE_ENOUGH_DATA);
    vi.advanceTimersByTime(20000);
    expect(audio.load).toHaveBeenCalled(); // v1.20.9 綠，v1.20.10 紅
    ```
- 影響：正正係用戶指定要保住嘅「凍結 playing 喺到期時都要 reload」。窗口有限（只影響 mark 附近先到嘅 `playing`，或者 park 後 rebuffer），而且鎖屏已顯示 Play、撳 Play 會即時 reload（`resume()` 讀實時 `isFrozenPlaying()`），所以唔係永久壞；但自動恢復會靜靜消失，用戶要自己發現冇聲先撳。
- 方案 A：凍結檢查獨立一個 timer。watchdog 加 `checkFrozenAfter(delayMs)`：每次 `playing` / `waiting` 都 `clearTimeout(frozenTimer)` 再排；到期時只喺 `this.overdue && this.hooks.isHidden() && this.hooks.isFrozenPlaying()` 先 `retryNow()`，否則乜都唔做；`cancel()` 一齊清。優：同輪詢 timer 完全解耦，兩個漏洞一次過封；`overdue` guard 保證永遠唔會早過 deadline。劣：多一個 timer field，`cancel` / `arm` 要記得處理。
- 方案 B：保留現有 `recheckWhenParked`，但 (i) `waitWhileHidden` park 時如果今次嘗試已發 `playing`，按「距凍結門檻仲有幾耐」排一次 recheck（要 AudioController 經 hook 提供 `msUntilFrozen()`）；(ii) `recheckWhenParked` 喺 parked recheck 已排時改為 clear 再排。優：改動貼近現有設計。劣：要分「輪詢 timer」同「parked recheck timer」兩種狀態，邏輯更易錯。
- 推薦：A。regression test 用上面兩個情境（mark 前 2 s 到嘅 `playing`；park 後 `playing → waiting → playing`），再加「健康 playing 喺 recheck 前出聲 → 唔 reload」同「前景唔會早過 deadline」。

### 🟡 Warning

#### W-510 — `stall.loading` 用 arm 嗰陣嘅 baseline，鎖屏時其實係「由開播起有冇載過嘢」

- 位置：`src/player/stallWatchdog.ts` `get loading()` / `isStillLoading()`；`waitWhileHidden()`（冇刷新 baseline）
- 描述：前景每次 recheck 都 `arm()` 刷新 baseline，所以「有進展」= 最近 ≤ 4 s 有進展。hidden 時 `waitWhileHidden` 唔 arm，baseline 停喺開播（或者最後一次前景 arm）。結果：開播頭 1 s 載咗少少、之後網絡死咗（S-551 情境 1），到 20 s 用戶撳鎖屏 Play，`loading` 仍然 true → 淨 `play()`，唔 reload；要等到開播後 30 s（`STALL_MAX_WAIT_MS`）先救得返。臨時 repro（buffer 0 → 0.5 → 1 s 之後停，20 s 撳 Play）證實 `load` 0 次、`isStalled` true。
- 影響：同用戶揀嘅方案 A 字面（「下載**仍然**有進展」）有落差；情境 1 鎖屏 Play 最多慢 ~18 s 先 reload，期間撳 Play 冇反應。唔會 abort 任何嘢，亦唔會令播放永久壞，所以係 Warning。
- 方案 A：`waitWhileHidden` 每個 tick（包括 park 嗰下）刷新 `baseline`（唔郁 `deadline`），`loading` 就係「上次 tick / park 之後有冇進展」。優：兩三行；同前景語義接近。劣：park 之後冇 tick，「上次」可能係幾十秒前（仍然好過開播嗰刻）；要小心唔好影響 `onDeadline` 前景分支用嘅 baseline（亮屏時會先 `retryIfOverdue`，用新 baseline 判斷反而更準）。
- 方案 B：AudioController 記 `lastGrowthAt`（`progress` event / `bufferedEnd` 增長時更新），`loading` = 未過 cap 且 `now - lastGrowthAt < STALL_PROGRESS_RECHECK_MS`。優：真正「而家仲載緊」。劣：iOS 鎖屏 JS 凍結，`progress` event 可能喺 mediaSession handler 之後先派發，鎖屏 Play 嗰刻讀到嘅 `lastGrowthAt` 可能過時 → 誤判冇進展而 reload，等於重開 v1.20.7 風險。
- 推薦：A（保守，唔會比現時更易 reload），並加 test：「頭 1 s 有進展之後停，20 s 鎖屏 Play → reload」。

## 修訂後代碼（C-011 方案 A + W-510 方案 A 示意）

```ts
// stallWatchdog.ts
/** playing / waiting 之後專睇凍結（同輪詢 timer 分開，C-011） */
private frozenTimer: ReturnType<typeof setTimeout> | undefined;

/** AudioController 每次 playing / waiting 叫：delayMs 後如果已過 deadline、hidden 而凍結就 retry */
checkFrozenAfter(delayMs: number): void {
    clearTimeout(this.frozenTimer);
    if (!this.pending) {
        return;
    }
    this.frozenTimer = setTimeout(() => {
        // overdue：永遠唔會早過原本 deadline；前景交返 onDeadline / visibilitychange
        if (this.overdue && this.hooks.isHidden() && this.hooks.isFrozenPlaying()) {
            this.retryNow();
        }
    }, delayMs);
}

cancel(): void {
    clearTimeout(this.timer);
    clearTimeout(this.frozenTimer); // C-011
    // …其餘不變
}
```

## 指定檢查：`checkFrozenIn` 會唔會令前景提早 retry — ✅ 唔會
