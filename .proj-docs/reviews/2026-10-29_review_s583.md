### 🟢 Suggestion

#### S-584 `playingFired` reset 冇綁死每一次 `audio.load()`

- 位置：`src/player/AudioController.ts` `recoverSource()`（`this.audio.load()`）vs `reload()`
- 描述：flag 嘅意思係「今次嘗試已發 `playing`」，而每次 `audio.load()` 都係新嘗試。`reload()` 有清，`recoverSource()` 冇。而家冇 bug，因為 `recoverSource()` 只喺 `audio.error` 時行，而 `onError` 一定 `stopWatchingStall()`，下一次 `play()` 必定經 `watchStall()` 新一輪清 flag；但呢個依賴係隱含嘅，將來 `onError` 唔再 cancel（或者 `online` 事件喺 pending 時觸發）就會靜靜咁將舊 `playing` 帶入新載入，令 rs 0→2 唔算進展（W-498 退化）。
- 方案 A（推薦）：抽 `private loadSource(): void { this.playingFired = false; this.audio.load(); }`，`reload()` 同 `recoverSource()` 都用。
    - Trade-off：多一個 3 行 helper；不變式寫死喺一處。
- 方案 B：喺 `onEmptied` 清 flag（load / 換 src 都會發 `emptied`）。
    - Trade-off：更貼 spec，但 `emptied` 係 queued task，同 `reload()` → `play()` → `playing` 嘅次序要逐個驗，而 FakeAudio `load()` 唔發 `emptied`，測試要跟住改。

#### S-585 `HAVE_*` readyState 常數三處各自定義

- 位置：`src/player/loadProgress.ts`（`HAVE_CURRENT_DATA`、`HAVE_FUTURE_DATA`）、`src/player/loadProgress.test.ts`（describe 入面 2 / 3 / 4）、`tests/fakeAudio.ts`（export 0–4）
- 描述：同一組 spec 值寫咗三次；`loadProgress.test.ts` 冇用 `tests/fakeAudio.ts` 已 export 嘅版本。
- 方案 A（推薦）：`loadProgress.test.ts` 改 import `tests/fakeAudio` 嘅 `HAVE_*`。
    - Trade-off：最細改動；src 同 test 仍然各一份。
- 方案 B：src 開一個 `mediaReadyState.ts` export 全部，`loadProgress.ts` 同 `fakeAudio.ts` 都 import。
    - Trade-off：單一來源；`tests/` import `src/` 要確認 tsconfig include 冇問題。

#### S-586 「暫停前嘅 playing 唔算」測試前提唔太似真 element

- 位置：`src/player/AudioController.test.ts` `ignores playing from before the pause when a new play starts slowly`
- 描述：`pausedBySystem()` 播過（`emitAudible`）之後 rs 仍然係 1，所以新一輪靠 `emitLoadedData()` 1→2 證明 reset。真 element 播過再暫停 rs 通常已經 ≥ 3，唔會再見 1→2。測試確實鎖住 `watchStall()` 嘅 reset（mutation 會紅），但前提同情境 2（暫停後 rs=4、buffer 增長、新 `playing` 未到）唔同。
- 方案 A（推薦）：改用更真實嘅前提：暫停時 `readyState = HAVE_ENOUGH_DATA`、buffer 少量；新 `play()` 之後 `playing` 未發、buffer 增長 → 4 s 唔 reload（舊 flag 未清就會當卡住）。
    - Trade-off：測試更貼實機；要多兩行 setup。
- 方案 B：保留現測試，加註解講明 rs 1→2 只係用嚟分辨 flag 有冇清。
    - Trade-off：零改動風險，但讀者容易誤會係實機路徑。

    private recoverSource = (): void => {
        if (!this.audio.error || !this.state.recording) {
            return;
        }
        this.pendingStart = this.state.currentTime;
        this.moveTo(this.pendingStart);

        this.moveTo(this.pendingStart);

## 測試洩漏問題（開發者提出）

**確認存在，記做 S-594。** 機制：

- `AudioController.test.ts` 有 24 個 `controller.attach()`，每個測試最尾自己叫 `detach()`。`expect` 失敗時 `detach()` 唔會行，`window` 嘅 `online` / `pagehide` 同 `document` 嘅 `visibilitychange` listener 留低。
- `tests/setup.ts` 嘅 `afterEach` 會清 `localStorage`（playback log），fake timer 亦會由 `useRealTimers()` 放棄，所以洩漏只係經 listener。
- `spends one retry when a late timer and a screen wake-up land together` 會 dispatch `visibilitychange`。留低嘅舊 controller 嘅 `retryIfOverdue()` 用 fake `Date.now()` 判斷已過期，喺今次測試嘅 log 寫多兩行 `retry`，所以見到 4 行而唔係 2 行。
- 今次兩輪 mutation 每次都見到呢個假紅（Round 1 三次、Round 2 兩次），證實會誤導除錯。

**需唔需要即刻修：唔需要。** 綠嘅時候冇影響（全部測試都行到 `detach()`），只係紅嘅時候多一個假紅，屬既有 test hygiene，唔係 S-583 引入。建議另開一個 test-only commit，唔好塞入呢條 fix branch。

### 🟢 S-594 測試失敗時 controller 冇 detach，listener 洩漏到後面嘅測試

- 位置：`src/player/AudioController.test.ts`（三個 `vi.useFakeTimers()` describe，行 437 / 614 / 896 附近）；同樣模式可能喺 `usePlayer.test.tsx`
- 影響：一個測試紅會連帶 `spends one retry ...`（同其他會 dispatch `visibilitychange` / `online` 嘅測試）一齊紅，誤導 root cause。
- 方案 A（推薦）：檔案頂層加 `const attached: (() => void)[] = []` 同 helper `attachController(controller)`（attach 之後 push detach），頂層 `afterEach` 逐個 detach 再清空；`detach()` 要做成 idempotent（重複 `removeEventListener` 本身冇問題，`stopWatchingStall()` 亦可以重複叫）。
    - Trade-off：要改 24 處 `controller.attach()`，但機械性；測試尾嘅 `detach()` 可以保留或者慢慢移除。
- 方案 B：只修受害者：`spends one retry ...` 只數自己 controller 嘅 log（例如用獨有 URL 過濾 `retry` 行）。
    - Trade-off：一行改動，但其他測試仍然會洩漏，下一個 dispatch 全域 event 嘅測試又會中。
- 方案 C：每個測試包 `try { … } finally { detach(); }`。
    - Trade-off：唔使 helper，但 24 個測試都加縮排，噪音大。

### 修訂後代碼（S-594 方案 A）

```ts
// src/player/AudioController.test.ts — 檔案頂層
/** 測試失敗時都要解除綁定：否則 window / document listener 洩漏到後面嘅測試（S-594） */
const detachers: (() => void)[] = [];
const attachController = (controller: AudioController): (() => void) => {
    const detach = controller.attach();
    detachers.push(detach);
    return detach;
};
afterEach(() => {
    detachers.splice(0).forEach((detach) => detach());
});

// 各測試：const detach = controller.attach();  →  const detach = attachController(controller);
```
