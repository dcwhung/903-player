## 指定檢查點（逐項）

### (1) hidden 時除咗 `resume()` 冇任何路徑 reload — ✅ 成立

- reload 入口只有三個：`StallWatchdog.retryNow → hooks.retry → retryStalled → reload`、`resume() → reload('remote')`、`recoverSource`（`online` / play 入面，唔係 reload 現有 src 嘅 load，冇改）。
- `retryNow` 只由 `onDeadline` 叫（grep 證實冇外部 caller）；`onDeadline` 第一個判斷就係 `wanted && isHidden()` → `waitWhileHidden()` return。
- `!wanted` 時行 `retryNow`，但 `retryNow` 入面 `!canRetry()` 或 `!pending` 即 `cancel()`，唔會 reload。
- `retryIfOverdue` 只由 `onVisibilityChange` 嘅 **visible** 分支叫，而且經 `onDeadline` 再判一次 hidden。
- 前景 timer 喺鎖屏之後先行（例如前景已 retry 一次，之後鎖屏）：test「should skip a later retry timer that fires after the page was hidden」鎖住。

### (2) 正常 4–5 s 鎖屏載入唔會令 mediaSession 變 paused — ✅ 成立

- `useMediaSession` 嘅 `playbackState = isPlaying && !isStalled ? 'playing' : 'paused'`；hidden 時 `onStalled` 只喺 `attemptStartedAt + 12 s` 之後先叫。4 s / 8 s 兩次 hidden tick 都唔報。
- AudioController test「lets a normal ~4.3 s locked load finish and play without reloading」+「shows the lock screen as stalled only after the hidden grace」鎖住。
- 12 s 相對 v1.20.6 log 4.07 s 有 ~3× 餘量，合理。

### (3) isStalled 唔會卡死 — ✅ 成立

- 清除點（`stopWatchingStall`）冇改：出聲（`checkAudible`）、`pause` / `ended`（`onStopped`）、換集（`switchTo`）、`error`、`play()` rejected、`resume()` reload 前。
- hidden mark 之後 iOS 自己載完出聲 → `checkAudible` 清；亮屏 retry → 新一輪，出聲先清（同前景 C-010 一致）。
- `hiddenStallReported` 只係 watchdog 內部去重 flag，每次 `startAttempt()`（start / retryNow）重設，唔會影響 controller state。
- 唯一「cancel 但唔清 isStalled」嘅路徑係 `retryNow` 用完次數 / `!canRetry`：前者係有意（留 Play 畀用戶撳），後者 `canRetry=false` 即 `!isPlaying && !playIntent`，必然已經經過 `onStopped` / `onError` 清咗。屬舊行為，冇改。

### (4) hidden 輪詢會終止、冇 timer 洩漏 — ✅ 成立（附 S-613）

- 每次 `waitWhileHidden` 先 `clearTimeout(this.timer)` 再 set，任何時候最多一個 timer；`cancel()`（出聲 / 停 / 換集 / dispose 嘅 `stopWatchingStall`）清走。
- 終止條件：`cancel()`、`canRetry()` 變 false（下一 tick → `retryNow` → `cancel`）、或者頁面變 visible（下一 tick 行前景路徑）。
- **冇次數上限**：一直 hidden + 一直想播 + 一直唔出聲 → 每 `STALL_PROGRESS_RECHECK_MS` 4 s 一 tick 直到 unlock。iOS 鎖屏 timer 本身多數凍結，桌面背景 tab 會 throttle，成本極低；但 mark 之後嘅 tick 其實乜都唔做（見 S-613）。

### (5) 亮屏只得一次 retry — ✅ 成立

- `retryIfOverdue` → `onDeadline`（visible）→ 慢網仲有進展就 re-arm、否則 `retryNow`；`retryNow` 之後 `watch()` 將 deadline 推到 +8 s，所以同一刻 hidden timer 再行（現在 visible）或者再有 visibilitychange 都唔再 overdue。
- 次數：hidden 期間冇扣，亮屏用第一次（`retry(STALL_MAX_RETRIES)`），test「should spend the first retry once the screen wakes up past the deadline」+ AudioController「reloads once when the screen wakes up past the deadline」/「…JS timers were frozen the whole time」鎖住。
- 註：亮屏時如果由 arm 到而家下載有進展、又未過 `STALL_MAX_WAIT_MS`，會先 re-arm 4 s 再判（W-498 舊規則）——即亮屏「最多一次」而唔係「必定一次」，符合設計。

### (6) 前景場景不變 — ✅ 成立

- 前景（`isHidden()=false`）時 `onDeadline` 同 v1.20.7 逐字等價（`wanted && isStillLoading` → re-arm，否則 `retryNow`）；唯一新增係 `retryNow` 叫 `startAttempt()`，只寫 hidden 專用欄位。
- S-583（重試入面 play 唔補次數 / 唔推 timer）、W-498 / W-500（慢網 recheck 唔扣次數、上限）、W-505（CUI-0011 progress 計數）、C-009（亮屏補做）、C-010（首 deadline 報卡住）嘅原有 test 全部唔使改就綠；新加「retries a stalled auto-advance after the shorter first timeout in the foreground」再鎖一次 v1.20.7 前景行為。

### (7) hidden 但冇鎖屏（切去第二個 app / 背景 tab）— ✅ 同一規則可以接受（附 S-615）

- iOS 切 app：同鎖屏一樣係背景 audio session，載入同樣慢、reload 同樣會 abort，套同一規則係**啱**嘅。如果另一個 app 搶咗 audio，我哋會收 `pause` → `onStopped` → watchdog cancel，唔會輪詢。
- 桌面 / Android 背景 tab：真係卡住時唔再自動 reload，要返嚟（`retryIfOverdue`）或者喺系統 media control 撳 Play（12 s 後顯示 paused → `resume()` reload）。用戶有明確恢復手段，桌面卡住本身罕見，trade-off 可接受；只係註解應該講清楚規則覆蓋所有 hidden（S-615）。

### 🟢 Suggestion

#### S-613 — hidden mark 之後輪詢冇上限、亦冇作用

- 位置：`src/player/stallWatchdog.ts` `waitWhileHidden()`
- 描述：報咗卡住之後，每 4 s tick 只係再問 `isHidden()`；變 visible 嘅情況 `onVisibilityChange → retryIfOverdue` 已經處理，鎖屏 Play 由 `resume()` 處理，所以 mark 之後嘅 timer 冇任何獨有用途，但會一直排落去。
- 影響：極細（iOS 凍結 timer；桌面背景 throttle）；純屬唔必要嘅工作同閱讀負擔。
- 方案 A：`hiddenStallReported` 之後唔再 `setTimeout`（`this.timer = undefined`），交返 visibilitychange / resume。優：最簡、意圖清楚。劣：倚賴 visibilitychange 一定會發（現代瀏覽器係）。
- 方案 B：保留輪詢但用 `STALL_MAX_WAIT_MS` 封頂。優：保守。劣：多一條規則。
- 推薦：A。

#### S-614 — 鎖屏 Play 喺正常但好慢（> 12 s）嘅載入仍會 abort 佢

- 位置：`src/player/AudioController.ts` `resume()` / `isSuspectedStall()`
- 描述：hidden 時過咗 4 s `overdue` 就已經係 true；mark 12 s 後鎖屏顯示 Play。慢網下載仍有進展時用戶撳 Play → `reload('remote')` → 同 v1.20.7 一樣 abort 載緊嘅數據，之後 iOS 背景可能再唔載完。屬用戶明確操作、只限 > 12 s 嘅慢載，唔阻 hotfix。
- 方案 A：`resume()` 喺 hidden 而且 `isLoadProgressing(baseline, probe)` 時只 `play()` 唔 reload（watchdog 要出一個 `isProgressing` getter）。優：堵死同一類 abort。劣：要再諗「進展但永遠唔出聲」點收尾。
- 方案 B：維持現狀，喺 CUI / 真機 log 觀察有冇人中。優：零改動。劣：慢網用戶可能再遇到。
- 推薦：B 先，收到真機 log 再做 A。

#### S-615 — 註解寫「鎖屏」，但規則係所有 `document.hidden`

- 位置：`src/config/constants.ts`（`STALL_FIRST_RETRY_MS` / `STALL_HIDDEN_MARK_MS` 註解）、`src/player/stallWatchdog.ts` class doc / `waitWhileHidden` doc
- 描述：`isHidden` hook doc 有寫「背景 / 鎖屏」，但其餘註解只講鎖屏；桌面背景 tab 唔自動 reload 係有意決定（見 (7)），應寫低，免得之後有人當 bug「修返」。
- 方案 A：加一句「切 app / 背景 tab 都一樣，唔自動 reload」。方案 B：將 hook 改名 `isBackground`。推薦：A。

## 修訂後代碼

唔使：今次 hotfix 按現狀 release。S-613 方案 A 參考：

```ts
private waitWhileHidden(): void {
    const untilMark = this.attemptStartedAt + STALL_HIDDEN_MARK_MS - Date.now();
    clearTimeout(this.timer);
    this.timer = undefined;
    if (untilMark > 0) {
        // 未到 mark：再睇一次（仍然 hidden 就再等）
        this.timer = setTimeout(this.onDeadline, Math.min(untilMark, STALL_PROGRESS_RECHECK_MS));
        return;
    }
    if (!this.hiddenStallReported) {
        this.hiddenStallReported = true;
        this.hooks.onStalled();
    }
    // mark 之後交畀 visibilitychange（retryIfOverdue）同鎖屏 Play（resume）：deadline 保持 overdue
}
```
