## 問題描述

v1.20.12 喺 metadata 未到前用 `fetching`（前景、`NETWORK_LOADING`、未 `stalled`）當進展。但 metadata 一到（`readyState` 0 → 1），`stillFetching` / `gotBytes` 都即刻唔再適用，而 `gotData` 要 `HAVE_CURRENT_DATA`（W-500：`HAVE_METADATA` 唔算進展），metadata 後嘅 `progress` 亦唔算（W-505）。如果 metadata 之後嗰個 4 s 窗口入面續播位置嘅 `buffered` 未有增長，就當冇進展 → reload → 由 byte 0 再嚟。

再加上 `STALL_MAX_WAIT_MS`（30 s）由第一次 `start()` 計：第一次 reload 喺 28 s，之後 30 s 上限已過，`isStillLoading()` 永遠 false，每 8 s reload 一次，header 永遠載唔完，要用晒 3 次重試先畀佢載完。

`1764 B / 100 ms`（0.1×，原本 CUI-0011 情境）冇呢個問題（metadata 13.15 s，playing 18.81 s，冇 retry）：metadata 後 4 s 窗口剛好見到 buffer 增長。所以係「metadata 到咗之後下一個窗口夠唔夠快見到 buffer」嘅邊界問題，網絡愈慢愈易中。

鎖屏開播後亮屏（0.05×）同一問題：亮屏冇 reload（✅），metadata 26.17 s，之後 27.33 s / 35.33 s reload。

## 影響

- 好慢嘅網絡（4 s 內載唔完 header、而 metadata 後 4 s 內續播位置未有 buffer）開播比 v1.20.11 更慢（57 → 81 s），亦白載咗一次 header
- 真 AAC header 細過 WAV，實際觸發門檻可能更低速；iPhone 行為未知

## 解決方案建議

- 方案 A（推薦）：`hasGrown` 加一條「metadata 啱啱到」：`before.readyState < HAVE_METADATA && after.readyState >= HAVE_METADATA && before.fetching` → 算進展。要小心 W-500（header 即刻到然後靜晒）：嗰個情境 metadata 喺 0.3 s 到、第一個窗口就包住，會將首次 retry 推到 8 s。可以只喺「今次嘗試已經用過 fetching 延期」（即唔係第一個窗口）先算，或者用 metadata 到達時間 ≥ `STALL_FIRST_RETRY_MS` 做條件
- 方案 B：metadata 後嘅 `progress` event 喺「metadata 前用過 fetching 延期」嘅嘗試入面都算（log 見 metadata 後 0.34 s 有 `progress`）。同 W-505 嘅分別一樣靠「唔係第一個窗口」
- 附帶：`STALL_MAX_WAIT_MS` 由第一次 `start()` 計，reload 之後新嘗試完全冇 fetching 延期，慢網每 8 s abort 一次。可以考慮 reload 之後 cap 由新嘗試計，或者 cap 過咗之後至少畀新嘗試一個 `STALL_RETRY_MS` 載 header。Trade-off：最壞情況總時間變長

## 驗證方式

- Chromium trickle 0.05×（QA script `qa1212/cui11.mjs c0slow100`）：metadata 後冇 retry，`playing` 早過 v1.20.11 嘅 57 s
- 0.1×（`c0`）、hang、W-505 shape（`w505`，首次 retry ≈ 4 s）照舊
- Unit：metadata 前 fetching → metadata 到、續播位置未有 buffer 嘅下一個 deadline 唔 reload；W-500 shape 首次 retry 仍然 4 s
