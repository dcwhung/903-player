## 問題描述

W-510 修正（`f16cc0a`）令每個 hidden tick 都經 `refreshHiddenBaseline()` 將 `baseline` 換成「而家」。W-511 / W-512 已經令鎖屏 Play 用嘅 `loading` 改為同 `previousBaseline ?? baseline` 比較，但**亮屏**走嘅係另一條路：

```text
visibilitychange (visible) → retryIfOverdue() → onDeadline() 前景分支
  → if (wanted && this.isStillLoading())   // since 預設 = this.baseline（最新 hidden snapshot）
```

`isStillLoading()` 冇傳 `since`，所以用最新嗰個 hidden snapshot。如果亮屏之前啱啱行咗一個 hidden tick（iOS 解凍時過期 timer 同 `visibilitychange` 一齊排隊，次序冇保證；或者單純喺 tick 之後好快亮屏），比較窗口 ~0 → 當冇進展 → `retryNow()` → `audio.load()` abort 緊個慢但仲載緊嘅下載。

v1.20.9（`17baeb8`）同 Round 1（`91b0aa2`）hidden 唔刷新 baseline，亮屏時同 arm 嗰陣比較 → 有進展就 `arm()` 再等，唔會 reload。

## 影響

- 用戶鎖屏慢網開播（或者鎖屏自動接住播下一集），載緊途中亮屏：慢載被 abort、由頭再下載，扣一次重試。前景 reload 之後通常播得返，所以唔係永久壞；但違反 W-498「前景慢網唔好 abort 進行中嘅下載」，而且比 v1.20.9 差（v1.20.9 唔會）。
- 窗口：今次嘗試頭 12 s 內（mark 前每 ≤ 4 s 一個 tick）或 mark tick 本身喺亮屏前一刻行；mark 之後冇 tick，除非 `frozenTimer` 啱啱行。
- Chromium 唔凍結 JS，e2e 冇呢個情境；要靠 unit test 鎖住。

## 解決方案建議

- 方案 A（推薦）：`onDeadline` 前景分支改為 `this.isStillLoading(this.previousBaseline ?? this.baseline)`（同 `loading` getter 一致）。`arm()` 會清 `previousBaseline`，所以純前景嘅 W-498 recheck 行為完全唔變；只有「hidden 之後第一次前景到期」先用上一個 snapshot。QA 喺 scratch copy（`8d4442f` + 呢一行）驗證：`src/player` 271 tests + QA 11 個 edge test 全綠。
- 方案 B：`onVisibilityChange` 亮屏時如果 `stall.loading` true 就先 `arm()` 再等，唔經 `retryIfOverdue`。劣：多一條路徑，同 C-009 補做邏輯分叉。

## 驗證方式

- 將上面 A、B 兩個 test 收錄入 `AudioController.test.ts`（v1.20.10 describe），HEAD 紅、修正後綠
- W-510 test（「reloads on lock-screen play when data stopped arriving long ago」）同 v1.20.8 「reloads once when the screen wakes up past the deadline」仍然綠（冇進展亮屏照 reload）
- Mutation：`onDeadline` 改返 `isStillLoading()` → A / B 紅
