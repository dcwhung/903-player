## 問題描述

W-498 用 `bufferedEnd` / `readyState` 增長判斷「仲載緊」。但 Chromium 喺 `loadedmetadata` 之前唔會公開任何下載進度：`buffered` 一直空、`readyState` 一直 0，即使 bytes 一直入緊。所以開播時如果網絡慢到 4 秒內載唔夠 demuxer 要嘅頭段，watchdog 會當「冇進展」照 reload；`audio.load()` 會 abort 個 request，下一輪又由 byte 0 開始，同一段頭永遠載唔完，直到 3 次重試用晒先畀佢載完。

QA 實測（Chromium、本機 HTTPS trickle server、CD 音質 WAV、17.6 KB/s ≈ 141 kbps，即係 0.1× 實時）：

```text
14:30:00.369 loadstart … 20261019_0600_在晴朗的一天出發.aac
14:30:04.297 retry ct=0.0 dur=NaN buf=- rs=0 ns=2 … left=3
14:30:12.306 retry ct=0.0 dur=NaN buf=- rs=0 ns=2 … left=2
14:30:20.316 retry ct=0.0 dur=NaN buf=- rs=0 ns=2 … left=1
14:30:33.481 loadedmetadata ct=0.0 dur=600.0 buf=- rs=1 …      ← 次數用晒之後先載完頭段
14:30:39.162 canplay ct=120.0 … buf=120.4 rs=3
```

- 呢次測試 Chromium 要約 230 KB 先發 `loadedmetadata`（WAV；真 AAC 可能少啲）
- 開播約 37 秒先出聲；同一個網絡如果冇 reload，大約 13 秒就有 metadata
- metadata 到咗之後嘅慢網（W-498 本身嘅情境）冇問題：0.1× / 0.5× trickle 都冇 retry（見 QA report §3 c）

## 影響

- S-551 之前前台普通撳播冇 watchdog，所以呢個係今次擴大 watchdog 範圍之後先有嘅行為
- 只有好慢嘅網絡（4 秒內載唔到開頭幾百 KB，約 < 0.5 Mbps）先會中；正常 4G / Wi-Fi 唔會
- iOS Safari 喺 metadata 前會唔會公開 `buffered` / `readyState` 進度未知（Chromium 量度唔代表 iPhone）

## 預期結果

下載仲有進展時唔 abort（W-498 嘅原意），或者至少唔好每次都由 byte 0 重新開始。

## 解決方案建議

- 方案 A（推薦，先量度）：下次 iPhone 實機測試（S-583 同一輪）喺慢網開播，睇 log 入面 `loadstart` 之後頭幾行嘅 `rs=` / `buf=`。iOS 喺 metadata 前已經有進度就唔使改
- 方案 B：未有 metadata 時（`readyState < HAVE_METADATA`）首個 deadline 用 `STALL_RETRY_MS`（8 秒）唔用 4 秒。Trade-off：S-551 情境 1（轉網絡之後完全冇數據）首次重試會遲 4 秒，正正係 W-500 想避開嘅
- 方案 C：用 `progress` event（spec 規定下載緊大約每 350 ms 發一次）做進度訊號，加入 `LoadProbe`。Trade-off：要喺 controller 記低最後一次 `progress` 嘅時間；iOS 會唔會喺 metadata 前發都要實機確認

## 驗證方式

- 實機：慢網（例如 Network Link Conditioner「Edge」/「3G」）開播，log 冇 `rs=0 buf=-` 嘅 retry，或者 retry 之後唔會由頭再下載
- Chromium：同上 trickle 測試冇 4 / 12 / 20 秒 retry
